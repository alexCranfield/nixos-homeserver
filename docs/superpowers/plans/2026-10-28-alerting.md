# Alerting Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Prometheus rules and Alertmanager post the nuc's event and
threshold alerts to the private Discord channel, through the existing
`homeserver-notify` sender.

**Architecture:** A rules file generated from one Nix attribute set of
thresholds and durations, unit-tested with `promtool`. Alertmanager on
loopback sends every alert, one per group, to a small Python relay. The
relay runs `homeserver-notify` for each alert. Two small sources fill the
gaps in the metrics: a Tailscale-state textfile and a blackbox exporter.
A VM (virtual machine) test drives the whole pipeline.

**Tech Stack:** NixOS 26.05: Prometheus 3.12.0 (`promtool`),
Alertmanager 0.31.1 (`amtool`), blackbox exporter 0.28.0, node-exporter
1.11.1, cAdvisor 0.56.2, Python 3 standard library.

**Spec:** `docs/superpowers/specs/2026-10-28-alerting-design.md`

## Global Constraints

- Everything listens on 127.0.0.1 only: Alertmanager **9093** (cluster
  listener off), relay **9095**, blackbox **9115**. No firewall port is
  opened.
- The relay posts through `config.homeserver.notify.sender`, with
  `homeserver.notify.webhookFile` and `roleFile`. There is no new secret.
  The URL never goes on a command line, into the store, or into the
  journal.
- Firing: icon `🔴`, title `nuc: <summary>`, pings the role. Resolved:
  icon `✅`, title `nuc: resolved: <summary>`, no ping (role argument `-`).
- Alertmanager: `group_by: ['...']`, `group_wait: 10s`,
  `group_interval: 5m`, `repeat_interval: 12h`, `send_resolved: true`.
- One inhibit rule: `GatewayUnreachable` suppresses `DnsFailing` and
  `TailnetDisconnected`.
- Deployed thresholds and durations are exactly the spec's tables. Tests
  override them through the option only, never by editing defaults.
- Expand acronyms at first use per document. Commit subjects under 72
  characters, with no attribution trailers.
- Never put NAS names or addresses, the tailnet name, or 100.x addresses in
  the repo. The DNS probe goes through the local resolver (127.0.0.53),
  never the Pi-hole's address.
- New units join `homeserver.notify.units`.

## Review Focus

1. An alert firing while another in the same rule resolves: only the
   change posts, and nothing is re-pinged. Pinned in Task 4: two
   `UnitFailed` alerts, one cleared.
2. The relay given a body Discord would choke on (2000+ characters, `@`,
   backticks in a label): it goes through `homeserver-notify`'s handling,
   never around it. Pinned in Task 3's unit test: a summary with `@everyone`
   and a fence reaches the sender unchanged, as one argument.
3. A Discord outage: the relay returns 5xx, and Alertmanager retries and
   delivers later. Pinned in Task 4: the receiver stopped, then restarted.
4. A watched unit failing gives exactly one post (the notifier's). Pinned
   in Task 4: kill cAdvisor and count posts over 90 s.
5. A stack without `memoryMax` never triggers `StackMemoryNearLimit` (its
   limit reads as huge or 0). Pinned in Task 1's promtool test: a slice
   with no limit series.

### Task 1: Rules and their promtool tests

**Files:**
- Create: `modules/observability/rules.nix`
- Create: `tests/alert-rules/` (promtool test YAML files, one per rule group)
- Create: `tests/alert-rules.nix`
- Modify: `flake.nix` (check `alert-rules`)

**Interfaces:**
- Produces: `rules.nix` is a function
  `{ lib, thresholds, watchedUnits }: { groups = [ … ]; }`, rendered by
  callers to YAML.
  - `thresholds` is an attrset keyed by alert name. Each value is
    `{ value ? number; for : string }`, with the spec's defaults.
  - `watchedUnits` is a list of names without `.service`.
- Produces: the option `homeserver.alerting.thresholds` (in Task 3), whose
  default is `rules.nix`'s exported `defaults` attrset.
- The full list of alerts: `TargetDown`, `UnitFailed`,
  `CominFetchFailed`, `CominEvalFailed`, `CominBuildFailed`,
  `TailnetDisconnected`, `GatewayUnreachable`, `DnsFailing`, `OomKill`,
  `DiskFilling`, `HostMemoryLow`, `HostCpuHigh`, `TemperatureHigh`,
  `ContainerCpuHigh`, `StackMemoryNearLimit`, `StackMemoryStalled`,
  `StackCpuStarved`.
- Every alert carries the label `severity` (`event` or `threshold`) and
  the annotations `summary` and `description`. The summary holds the value
  and the threshold, for example `Disk / is 87% full (threshold 85% for
  10m)`.
- Metric names the rules use for the textfile:
  `homeserver_tailscale_running` and
  `homeserver_tailscale_health_messages`. Task 2 produces them.
- Blackbox jobs: `blackbox_gateway` and `blackbox_dns`. Task 2 produces
  them. Rules use `probe_success{job=…} == 0`.

- [ ] **Step 1: Write the promtool tests.** Per alert:
  - one case that fires at exactly its `for:`;
  - one case just short of it that doesn't;
  - one case just below the threshold that doesn't.
  
  Plus:
  - `UnitFailed`: fires for `foo.service`; doesn't for `sshd.service`
    when `sshd` is in `watchedUnits`.
  - `TargetDown{job="cadvisor"}`: doesn't fire while

  - `OomKill`: fires on a counter rise of 1, with `for: 0`.

### Task 3: Alertmanager, the relay, and Prometheus wiring

**Files:**
- Create: `modules/observability/alerting.nix`
- Create: `modules/observability/alert-relay.py`
- Create: `tests/alert-relay.nix` (runs the relay's unit tests, no VM)
- Modify: `modules/observability/default.nix` (import; Grafana data source
  `alertmanager`, uid `alertmanager`, `implementation: prometheus`)
- Modify: `flake.nix` (check `alert-relay`)

**Interfaces:**
- Consumes: `rules.nix` (Task 1), with `watchedUnits =
  config.homeserver.notify.units`.
- Produces: the option `homeserver.alerting.thresholds`, as in Task 1.
- Produces: `alert-relay.py`'s pure function
  `messages(payload: dict) -> list[tuple[str, str, str, bool]]`. Each
  tuple is (icon, title, body, ping), one per alert in
  `payload["alerts"]`. Its CLI (command-line interface) is
  `alert-relay.py SENDER WEBHOOK_FILE ROLE_FILE HOST PORT`.
  - It serves `POST /` and calls
    `SENDER WEBHOOK_FILE (ROLE_FILE|-) ICON TITLE` with the body on stdin,
    via `subprocess.run` with an argument list (no shell).
  - It replies 200 if every post succeeded, else 500.
- Produces: `alert-relay.service`, run as a dynamic user. It gets the
  webhook and role files through `LoadCredential=`, as `notify-failure@`
  does, and is added to `homeserver.notify.units`.
- Body: the `description` annotation. For a resolved alert, the body adds
  how long it lasted, from `startsAt` and `endsAt`.

### Task 4: End-to-end VM test

**Files:**

- Modify: `flake.nix` (check `alerting`)

**Interfaces:**

- The test overrides `homeserver.alerting.thresholds` with short `for:`

  Deployed values are untouched.

- [ ] **Step 1: Write the subtests**, each checking the post's title, its
  icon, whether it pings, and then its resolved post:
  1. `TargetDown`: stop node-exporter with a clean stop. One 🔴, then ✅
     after a start. Record the seconds from stop to post.
  2. `UnitFailed`: `systemd-run --unit fail-me false`. One post. Negative
     control: kill cAdvisor (`systemctl kill -s KILL`) and wait 90 s.
     Exactly one new post, the notifier's (Review Focus 4).
  3. `DiskFilling`: the low threshold fires. Raising the threshold back
     through a `specialisation` is too slow, so fill a file and check that
     resolution follows its removal.
  4. `TailnetDisconnected`: the textfile reports 0 (this VM isn't logged
     in), so it fires. The inhibit check: also force `GatewayUnreachable`
     (the gateway option is an address nothing answers). Only
     `GatewayUnreachable` posts, not `DnsFailing` or `TailnetDisconnected`.
     Ruling allowed: if both can't be arranged in one VM, use two test
     nodes.
  5. `OomKill` and `StackMemoryNearLimit`: a stack-like slice
     `stack-oomtest.slice` with `MemoryMax=64M`, and a busybox container
     with `--cgroup-parent` set to it, allocating past the limit. One
     `OomKill` post.
  6. Two firing, one resolving: fail two `UnitFailed` units, then
     `reset-failed` one. The other isn't posted again (Review Focus 1).
  7. A silence: `amtool silence add alertname=TargetDown --duration 10m`,
     then stop node-exporter. No post in 60 s.
  8. A Discord outage: stop the receiver, trigger `UnitFailed`, wait
     30 s, start the receiver. The post arrives (Review Focus 3).
  9. Loopback only: 9093, 9095 and 9115 bound to 127.0.0.1, and the 9094
     cluster port absent.
  10. The webhook secret is not in the journal.

  Run: `nix develop -c just vm-test-tcg alerting`. Expected: a FAIL in
