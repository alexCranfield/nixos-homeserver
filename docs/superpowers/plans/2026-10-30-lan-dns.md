# LAN DNS (#164) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Blocky and Unbound on the nuc serve the house's DNS (Domain Name System) with blocking, a query log in PostgreSQL, a Grafana dashboard, and Discord alerts for failures and suspicious activity, while the nuc itself resolves through the router.

**Architecture:** A new `modules/dns/` (Blocky, Unbound, the query log, the suspicious-activity timer) imported by `hosts/nuc`. The router's address becomes one option in `modules/base`. Probes and rules extend `modules/observability/`. One new VM (virtual machine) test, `tests/dns.nix`, with router, client and NAS stand-ins; rule thresholds are unit-tested with promtool.

**Tech Stack:** NixOS 26.05 modules: `services.blocky` (0.29.0), `services.unbound` (1.26.1), `services.postgresql` (17), `services.prometheus.exporters.unbound`, the existing blackbox exporter, sops-nix templates.

**Spec:** `docs/superpowers/specs/2026-10-29-lan-dns-design.md` (approved 2026-10-30). Read it before any task.

## Global Constraints

- **Never write a private name into any repo file, commit, PR or issue:** the NAS's name or address, the tailnet name, Tailscale 100.x addresses, the ULA prefix, Alex's email, friends' player names. The NAS's address reaches the nuc only through sops. Scan every diff for them before committing (the controller holds the list; it is not written here).
- Alex creates and edits `secrets/*.yaml` himself. No task creates, encrypts or decrypts a secrets file; a task that needs one stops and asks the controller.
- IPv4 only. Port 53 UDP and TCP opened on `lan0` only. Blocky's HTTP port, Unbound, the Unbound exporter and PostgreSQL listen on loopback or a Unix socket only.
- The nuc's own resolver is the router, never Blocky.
- The query log: 14 days retention, not backed up, peer authentication over the socket, no password.
- Lists split into groups `ads` and `threats` exactly as the spec's Blocking section lists them; the cutover keeps those six lists (in formats Blocky reads).
- Each alert's threshold and `for` live in `modules/observability/rules.nix` `defaults`, tunable through `homeserver.alerting.thresholds`.
- Comments and docs follow CLAUDE.md: expand acronyms at first use per file, match the surrounding comment density and tone.
- Commits: imperative subject under 72 characters, no `Co-Authored-By` or session trailers.
- Nix commands: source `/nix/var/nix/profiles/default/etc/profile.d/nix-daemon.sh` first. Local VM tests run only under TCG: `nix develop -c just vm-test-tcg <name>` (slow; budget up to an hour for `dns`). Never `just deploy`.
- CI's job limit is 90 minutes, and a host change reruns every VM test (about 70 minutes before this ticket). Record the `dns` test's TCG duration in its report; the controller decides with Alex if CI would exceed the limit.

## Review Focus

1. **Boot ordering:** Blocky binds `192.168.1.131:53`, which exists only after DHCP on `lan0`; at boot it must end up running, not failed. Pinned by Task 2's reboot subtest.
2. **Lists that load empty:** a list in a syntax Blocky can't parse, or one that can't be downloaded, must not stop resolution, and must make the "not blocking" probe fail. Pinned by Task 2 (an unreachable list URL) and Task 4 (probe fails with no lists).
3. **PostgreSQL down:** resolution continues when the query log can't be written. Pinned by Task 3's subtest that stops PostgreSQL.
4. **A device with no reverse name:** it appears in the log and the metrics under its address, and the timer doesn't fail. Pinned by Task 5 (the client has no name in the router stand-in).
5. **The private hosts file and NAS address never in the Nix store:** pinned by Task 2 and Task 4 subtests that grep the closure.

### Task 5: Suspicious-activity metrics and alerts

**Files:**
- Create: `modules/dns/watch.nix`, `modules/dns/watch.sql`
- Modify: `modules/dns/default.nix`, `modules/observability/rules.nix`, `tests/alert-rules/dns.yml`
- Test: `tests/dns.py`

**Interfaces:**
- Consumes: the query log and role `dns-watch` (Task 3); node-exporter's textfile directory (`/var/lib/prometheus-node-exporter-text`, `probes.nix`).
- Produces: `dns-watch.timer` (every minute) writing `dns-watch.prom` with:
  - `homeserver_dns_threat_blocks{client, domain}`: count in the last 5 minutes of lookups blocked with reason containing `threats`.
  - `homeserver_dns_nxdomain_recent{client}` and `homeserver_dns_nxdomain_baseline{client}`: NXDOMAIN answers per minute over the last 10 minutes, and over the previous 7 days (or the log's span, if shorter).
  - `homeserver_dns_new_client{client}`: 1 for a client whose first entry in the log is within the last 10 minutes.
  - `homeserver_dns_watch_success`: 1 when the queries ran.
  - `client` is the client's name, or its address when it has none.
- Rules (`defaults` in `rules.nix`): `DnsThreatBlocked` (`> 0`, `for` 0s, event, summary names client and domain); `DnsNxdomainBurst` (recent `> 10` per minute and `> 5 ×` baseline, `for` 5m, threshold); `DnsNewClient` (`== 1`, `for` 0s, event); `DnsWatchFailing` (`homeserver_dns_watch_success == 0` or absent, `for` 10m).

- [ ] **Step 1: Write the failing rule tests** in `dns.yml`: each fires and stays quiet at the edges of its threshold and `for`; `DnsNxdomainBurst` stays quiet for a device whose baseline is already high (60 a minute at 70).
- [ ] **Step 2: Watch them fail.**
- [ ] **Step 3: Write the failing VM subtests.**

```python

    dig("threat.test")
    wait_for_metric('homeserver_dns_threat_blocks{client="%s",domain="threat.test"}' % CLIENT_IP, ">0")
with subtest("an NXDOMAIN burst raises the recent rate"):
```
